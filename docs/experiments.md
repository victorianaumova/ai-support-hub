## Known limitations (P7-07)

Recorded by owner decision after one quality pass; the red lines are not changed, and auto-reply stayed off (ADR-0018) until the owner allowed it in the cloud demo ([ADR-0022](adr/0022-auto-reply-on-in-the-demo.md)).

- **Citation validity: 4 of 9 answered tickets have an invalid marker (red line: 1).** Run `2026-11-20-rag_hybrid-585ce6a`, tickets T-0001, T-0008, T-0013 and T-0018. This run has no error analysis of its own (no further tuning, owner decision), so the failures are not classified. T-0001 fails on marker 5 (`payment-request-card-availability#1`), the same source the base run's analysis called a judge error, so it is probably a repeated judge error, unchecked. In T-0018 a marker is reused for a sentence its source does not state. The T-0013 draft ends with a literal `[CONTINUE]` and has unmarked sentences that apply a limit to the customer ("does not fit within the remaining amount"). That is a writer defect `write/v5` did not prevent, and the faithfulness judge (v3, same model family, unvalidated) did not flag it, so the faithfulness result of 0 of 9 is optimistic. An operator reviews every draft, so these reach the operator, not the customer.
- **Key-fact coverage: 0.73 on 9 tickets (red line: 0.75).** This is less than one ticket's worth below the line. In the base run's error analysis, 5 of the 16 missing key facts were in sections that the search did not find (T-0013, T-0018, T-0009). No prompt change can reach those. Another 2 cannot be reached at all: T-0008 key facts 2 and 3 are in no knowledge-base article (see the T-0008 open question below).

## Open questions (for a later pull request)

From the error analysis of the B0 run. Nothing here is changed yet; the owner decides.

**Labels** (`data/eval/tickets.dev.jsonl`; a fix gets a note in `data/eval/CHANGELOG.md`):
- **T-0008, key fact 2.** "Pending card payments count toward the daily card spend limit" is in the world file (`docs/tallybridge-world.md` line 37) but in no external article, so a writer grounded in the knowledge base cannot reach it. Either add it to an article (account-limits or card-declined) or drop the key fact.
- **T-0005, key fact 3.** "Check the bank details and create the withdrawal again": the customer's history already says the bank details were checked, so this key fact is weak.
- **T-0015, intent.** `login_security` against `card_lost_stolen` is borderline ("someone has my card or my account"). The label fits world §9; the routing effect is the same through the fraud flag.

**Judge.** The faithfulness judge does not see the ticket, so a draft that restates the customer's message is always unsupported, and a sentence that mixes customer context with an article fact fails its citation. Options: give the judge the ticket as context. Turn the wrong verdicts of T-0007 ("use another way to pay"), T-0009 and T-0018 into judge unit tests with recorded responses (eval plan §5). *Done in P5-03 (not measured yet):* `judge_faithfulness/v2` and `judge_citation/v2` see the ticket; the rules are in eval plan §4 ("Judges in the run"): a framed restatement ("you say ...") is not a claim; a customer statement written as fact is; a framed statement placed next to a rule so that the rule seems to apply is a claim too (owner decision), judged by faithfulness only. T-0007 is a recorded case. T-0009 is a key-facts verdict, out of scope. **T-0018 is still open.** The B0 baseline above was judged with `judge_*/v1`; any later run uses v2, so a `BASE=` comparison with it mixes judge versions and its faithfulness and citation numbers are not comparable.

**Write prompt v2.** One grounding rule: say nothing about the customer's own account or situation that no document or account fact says (no reassurance, no guessing a merchant type or which fee was charged), do not restate the customer's message, and put only facts from the cited document in a marked sentence. Expected effect: removes about 5–6 real unsupported claims; it will not reach the faithfulness red line alone. Measure with an owner-approved `make eval` (triage cached) and `make eval-report BASE=2026-11-17-b0_full_kb-4bc48fc`; key-fact coverage must not drop by more than one ticket's worth. *Done in P5-03 as part of `write/v2` (the writer with retrieval). From P5-05 the runner runs the RAG variants; their runs are judged with `judge_*/v2` and are not compared with the B0 baseline, which was judged with v1 (no `BASE=` comparison: it would mix judge versions).*
