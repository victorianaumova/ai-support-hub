# Security and Privacy

Scope: threat model, guardrails, access control, audit, privacy, regulatory duties. The project follows the ideas of PCI DSS and GDPR; it is not certified. In public text use the wording "designed with PCI-DSS-inspired constraints", never "PCI DSS compliant".

## 1. Assets and trust boundaries

| Asset | Why it matters |
|---|---|
| Card data (PAN, CVV, PIN), 2FA codes | Must never be stored or sent out. |
| Customer personal and account data | GDPR; one customer must never see another's data. |
| Internal knowledge (procedures, compliance wording, restriction reasons) | Leak = legal problem (tipping-off) and help for fraudsters. |
| Tool credentials and API keys | Money and access. |
| Audit log | Evidence; must be complete and unchanged. |
| Model budget | A public demo can be abused. |

Trust boundaries: (1) browser ↔ Hub API — all input untrusted; (2) Hub ↔ model providers — only masked data crosses; (3) Hub ↔ MCP server — authenticated, tools validate arguments again; (4) model output ↔ Hub code — model output is untrusted input for the code.

## 3. Guardrails

| ID | Guardrail | Where | Behaviour |
|---|---|---|---|
| G1 | **Card-data masking** | `guardrails/masking.py`, called by the API before anything else, again on operator text, and on every model-written string before it is stored (draft, missing information, proposed actions, triage summary; P3-05, `OutputMask` in `graph/draft.py`) | Finds runs of 13 or more digits with up to five separator characters between two digits (whitespace, dashes and minus signs, `+ . / _ ( )`, a comma not followed by a space, soft hyphen, middle dot, zero-width characters, URL-encoded space, plus or dash). A run of 13–19 digits that passes Luhn, or a run of 14 or more digits with any Luhn-valid part of 13–19 digits (a card with a number, CVV or expiry next to it), is replaced as a whole with `[CARD ****1111]` (last 4 only). A valid IBAN (country code from the ISO 13616 registry, that country's exact length, mod-97 check) is partly masked: `[IBAN DE89 …3000]` keeps the country code, check digits and last 4 characters (ADR-0017), so card digits inside it are never stored. When digits follow the IBAN, after a separator or directly (any Unicode digit), its last 4 are hidden too (`[IBAN AT77 …]`). The following run is masked as a card when it holds one itself; and, only when it has 5 or more digits and is not a PIN, 2FA or CVV code by the trigger rules, when a Luhn-valid 13–19 digit number crosses the IBAN's end. Such a crossing card is shown as `[CARD ****]`, without digits. Text that looks like an IBAN but is not valid is checked as a card number. PINs, 2FA codes and CVV-like numbers next to trigger words (`cvv`, `cvc`, `security code`, `code on the back`, `pin`, `2fa`, `otp`, `one-time code`, `verification code` …) → `[REDACTED]`. An exact error code `ERR-` + 4 ASCII digits `0-9` (uppercase `ERR`, no letter, digit or `_` directly before it) is not a PIN or 2FA code, so `ERR-3007 wrong PIN` keeps the code for triage; `ERR-30071 PIN`, `err-3007 PIN`, `ERR 3007 PIN`, `_ERR-3007 PIN` and `ERR-３００７ PIN` (full-width digits) are still masked, and the CVV rule has no such exception. A 3–4 digit number directly next to a masked card or an expiry date (at most three spaces or punctuation characters between) is a CVV too. Expiry dates: `MM/YY` or `MM/YYYY` (not inside a full date such as `03/14/2026`), and `MM-YY` or `MMYY` only right after `exp`, `expiry` or `valid until`. `code` right after a masked card is a CVV word. Amounts stay visible: no CVV when a currency sign or code is next to the number (`€`, `$`, `EUR`, `USD`, `GBP` …), when a decimal part follows (`250.00`), or when a label and colon come before a card (`Order 1234: …`). Digits after "ending" or "last 4" are not a CVV; PIN and 2FA codes are masked there too (except an exact error code). A token that is exactly a canonical UUID (8-4-4-4-12 hex digits; no letter, digit, `_` or dash joined to it, and no digit within a separator before or after it) is kept unmasked (owner decision, P8-03): ticket, customer and operator ids in log records, traces and the audit log stay searchable (about 1 in 100 UUIDs held a Luhn-valid run across its dashes). Returns counts by type (`PAN`, `CVV`, `PIN`, `2FA`, and `IBAN`, which is not card data). Never raises on odd input; on an internal error it replaces every digit and marks the result as failed. The input size is limited by the API (T9), not by this function. |
| G2 | **Outbound scan** | `llm/gateway.py` | Before every model call, scans the full request for card patterns and raw IBANs (G3 should have replaced them; a masked `[IBAN DE89 …3000]` is not a hit). A hit blocks the call, writes an audit record `guardrail.blocked` with `reason` `card_data` or `iban` (card data wins when both are found; `llm_calls.error` is `blocked: G2` or `blocked: G2 IBAN`) and fails the node (→ handoff). This catches programming mistakes. |
| G3 | **PII placeholders** | `guardrails/placeholders.py`, called by `intake` | Email, phone, IBAN → `<EMAIL_1>`, `<PHONE_1>`, `<IBAN_1>` in model input. Phone numbers are matched conservatively (international `+`/`00`, a national number starting with `0` with at least 9 digits, or `(555) 123-4567`), so amounts, dates, times and error codes are not taken for one; a number never starts right after a digit and a space or dash (so `1 000 000 000` stays an amount, and a phone number written right after one, as in `Option 2 0151 2345678`, is missed); a reference or account number that starts with `0` and is long enough is (owner decision, P3-04: hidden from the model, nothing leaks). A placeholder the customer typed (`<EMAIL_1>`) is written as `&lt;EMAIL_1&gt;`, so it is never restored. One mapping serves the whole run: `replace_pii(text, mapping)` continues it, so the ticket, the history and follow-up messages never use one placeholder for two values. G1 has already masked the IBAN (`[IBAN DE89 …3000]`); restoring gives that masked form, never a full IBAN (ADR-0017). The mapping stays in memory for the run. Placeholders are restored only if the answer must repeat them (normally it must not). |
| G4 | **Injection heuristics** | `guardrails/injection.py` | Pattern score (override phrases, role-play requests, prompt-extraction phrases, fake markup such as data or role tags, role tags in brackets or chat-template pipes (`[system]`, `<|system|>`; P8-02, same weight 0.4) and a `System:` line, encoded blocks, requests to decode and follow, forced output such as "reply only with"; each group has a weight, the score is their sum capped at 1). The score is in `input_flags.injection`; a high score **or** the triage flag `injection_suspected` hands the ticket off (reason `injection`; owner decision, P6-02). "High" is a score of at least `injection.high_score` in `config/policy.yaml` (0.5). It is a signal, not the defence — the defence is T2–T5 controls. Both the score and the tag neutralisation work on a folded view of the text (NFKD; format characters such as zero-width spaces, combining marks such as variation selectors, and Hangul fillers removed; case-folded; common Cyrillic/Greek look-alike letters and angle-bracket look-alikes mapped to ASCII). The same module neutralises data tags (`</ticket>`, `<kb>`, …) inside every value a prompt inserts (ai-pipeline §7). |
| G5 | **Policy gate** | `guardrails/policy.py`, `graph/nodes/decide.py`, `api/admin_settings.py` | Deterministic routing rules from `config/policy.yaml`. **Auto-reply lock** ([ADR-0019](adr/0019-scope-cuts.md), owner decision, P10-02): `AUTO_REPLY_ALLOWED` (default `false`) is a deployment setting, not a console one. While it is false, `PUT /admin/settings` refuses `auto_reply_enabled: true` (`409 auto_reply_not_allowed`, nothing written), and `decide` ignores a stored `auto_reply_enabled` and routes every draft to an operator (`approval`, reason `auto_reply_off`) — defence in depth against a row changed behind the API's back. Tests: `integration/test_metrics_api.py::test_switching_auto_reply_on_is_refused_while_the_deployment_does_not_allow_it`, `integration/test_graph_run.py::test_a_stored_auto_reply_setting_is_ignored_while_the_deployment_does_not_allow_it`, `unit/test_graph_nodes.py::test_decide_never_auto_replies_while_the_deployment_does_not_allow_it`. |
| G6 | **Tool permissions** | `tools/permissions.py` | Allow-list per node, identity injection, argument validation, limits per ticket, approval requirement for side effects. P7-03: allow-lists `intake` → `core_get_customer`; `research` → the four core read tools and `search_kb` (P7-04: a Hub tool, decided and recorded like the others); `handoff_prep` → `slack_post_escalation`; `act` → `jira_create_issue`; `console` → `core_get_customer`, `core_get_cards`, `core_list_transactions` (the operator's account view, `GET /console/tickets/{id}/account`, recorded under the ticket's latest run; read tools only; owner decision, PR #66); anything else is `denied`. Calls per node and run: research 5, console 30 (ten views of the account tab), the others 1 (denied calls count), counted from the run's `tool_calls` rows of that node (P7-04), so a resume or a second session of the run continues the count. The scope is built from the tickets row (`customer_ref` = the `customers.external_ref` of the ticket's customer, `hub/graph/tools.py`), and before a call that injects `customer_ref` the client checks it against the ticket's customer in the database (`invalid_identity` otherwise). No caller, model or code, may pass `customer_ref`, `ticket_id` or `idempotency_key`: they come from the run state, and a call that carries one is denied, recorded in `tool_calls` (argument names only) and audited (`tool.denied`, reason `identity_argument`). Unit-test rule: G1, G2, G5, G6, G7 need ≥ 95% line coverage and property-based tests (Hypothesis) for masking: any valid Luhn number in any common format inside random text must be masked.

**Known limitations of G1** (accepted by the owner in P2-03; each one is a case for the attack suite, P8-01):
- Rare separators are not recognised, so a card written with them is kept: `:` `;` `'` `|` `*` `~` `=` `\`, brackets or quotes around each group (`[4111][1111]…`), and invisible characters other than the zero-width ones listed above (e.g. U+2062, U+180E).
- IBANs (ADR-0017): every valid IBAN is stored partly masked, so the full IBAN is lost (accepted). An IBAN written with other separators (NBSP, dashes), in lowercase, or from a country added to the registry after release 101 is not recognised as an IBAN: its digits are checked as a card number only, so it may be stored in full or masked as a card. A number joined to a valid IBAN hides the IBAN's last 4. A number of 5 or more digits joined to it that is not a code by the trigger rules is almost always masked as `[CARD ****]` and counted as a PAN (it sets the customer's card note, and G2 reports `card_data`). In a measurement of 2,000 random numbers per length after one space (seed 17; the DE89 example IBAN, and random valid IBANs with all-digit account parts): 1–4 digits 0%; 5 digits 91–97%; 6 digits 95–99%; 8 or more digits 99–100%. A code of 4 or fewer digits after an IBAN is never taken for a card.
- Error codes next to PIN or 2FA words (pre-H2 #2): a PIN or 2FA code written as an error code is kept, e.g. `my PIN is ERR-1234` stores `1234`. Accepted so that triage sees the real error codes; a case for the attack suite (P8-01).
- A trigger word reaches only the first number after it: the gap to its code holds no digits, so in `PIN 5555 1234` or `PIN ERR-1234 5678` the last number is kept. Since error codes next to PIN and 2FA words are now kept (pre-H2 #2), such texts are more common.
- Over-masking (information lost, no leak): a 3–4 digit number after `MM/YYYY` (`05/2025, 1200 payments`) or before a card without a colon (`Order 1234 [CARD ****1111]`) is masked as a CVV; lists of numbers joined by ` - `, `/` or spaces with 14 or more digits can be read as one card; triggers such as `pin` also catch years (`pin changed in 2025`).
- IBANs masked as a card (attack-suite probes, P8-01): the lowercase and the dashed form of the DE89 example IBAN are masked as `[CARD ****…]` and counted as a PAN (the customer's card note is set, the IBAN information is lost). No leak; accepted, no change (owner decision, P8-02).
- UUIDs (owner decision, P8-03): a card number or a code written in the shape of a canonical UUID (`41111111-1111-1111-1111-111111111111`) is kept. A UUID with a digit within a separator before or after it is masked like any text, so a card cannot be split across a UUID's edge.
- Cost: masking is CPU work, about 12 ms per KB of digit-heavy text. The API limits input to 4,000 characters (T9, P2-06); log records have no size limit yet.

## 4. Authentication and authorisation

- **Operators:** email + password (Argon2id), session cookie, 8 hours, CSRF token for state changes, login rate limit, lockout after 10 failures. Demo accounts are created by a seed command with passwords from environment variables. Details (`hub/auth/`, `hub/api/auth.py`):
  - *Cookie:* `hub_operator` holds the operator id and `operators.session_version`, signed with `SESSION_SECRET` (its own salt, so a customer cookie is never an operator session) and expires 8 hours after login. Every request reads the operator from the database: an inactive operator or an older `session_version` has no session, and the role used for checks is the stored one, so a demotion applies at once.
  - *Logout ends all sessions of that operator:* logout (and a password change) increases `session_version`, so every cookie issued before, a copied one too, stops working. There is no per-browser logout.
  - *CSRF:* the token is an HMAC of the session cookie with a key derived from `SESSION_SECRET`. It is returned only in the bodies of `POST /auth/login` and `GET /auth/me`; the console sends it in `X-CSRF-Token` on every request that is not `GET`/`HEAD`/`OPTIONS` (`/console`, `/admin`, `/auth/logout`). A wrong or missing token → `403 csrf_failed`.
  - *Login failures* all answer `401 invalid_credentials` (unknown email, inactive operator, wrong password and locked account look the same; an unknown email is checked against a dummy hash, so it costs the same time). Two limits: 5 failures per 15 minutes per IP (in process memory, like the other rate limits), and the account lockout: the 10th wrong password locks the account for 15 minutes. The lockout lives in the database (`operators.failed_logins`, `locked_until`), because Cloud Run scales to zero and a lock in memory would reset too often. While locked, even the right password is refused. A lock ends by itself: a permanent one would let anyone who knows an operator's email lock that operator out for good. A successful login clears the count.
- **Roles:** see [API](api.md) §1. Role checks are FastAPI dependencies (`RequireRole`, which also checks the CSRF token); every console route declares its minimum role; a test walks all routes and fails when a route has no role. Answers: no session → 401, bad CSRF token → 403 `csrf_failed`, role not allowed → 403 `forbidden`.
- **Browser hardening (P8-04):** both cookies are `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, 8 hours (`Max-Age=28800`); the logout deletion carries the same flags. Every response has a strict Content-Security-Policy and the other security headers of [API](api.md) §1 (`hub/api/security_headers.py`, outermost middleware, so a 413 or a last-resort 500 has them too); `/api/...` answers are `Cache-Control: no-store`. The web app renders every written text by the safe rendering rule of [UI](ui.md) §2: text nodes only, a small Markdown subset, no links except the server-built `/help/...` citations (the customer API drops any other citation url, `safe_citation_url`), no images. A test walks every state-changing route behind `RequireRole` and checks that a missing, wrong or empty CSRF token is refused before the body and the role are checked; another table checks the length limit and the NUL refusal of every free-text request field.
- **Customers (demo):** the picker creates a signed session for a seed customer after the access code. It stands in for the real app login and is marked as demo-only in the code.
- **MCP server:** in production only the Hub can call it (Cloud Run "require authentication": the Hub's service account has the invoker role), plus a bearer token as a second check (`MCP_SERVER_TOKEN`, constant-time comparison; the HTTP transport refuses to start without one, P7-01). The server validates every argument again (reference formats, enums, lengths) and enforces the T8 limits itself: one Jira issue and one Slack alert per ticket, idempotency keys, both as unique indexes in its mock store.
- **Scheduled jobs:** `POST /admin/jobs/*` accepts only the `JOBS_TOKEN` bearer token (constant-time comparison). The token gives no access to any other endpoint. Every job run writes an audit record.
- **What a real company would add:** single sign-on with multi-factor authentication for operators. The demo uses passwords; the auth module is small and can be replaced ([ADR-0016](adr/0016-web-ui-and-auth.md)).
- **Least privilege for the database:** the application role cannot `UPDATE` or `DELETE` the audit log; migrations run with a separate role.

## 5. Audit log

Events (each with actor, entity and masked details): `ticket.created`, `message.received` (a customer message on an existing ticket), `feedback.created`, `auth.demo_session`, `guardrail.masked`, `guardrail.blocked`, `intake.done` (entity the run: injection score, pattern group names and placeholder counts by type, P3-05), `triage.done` (the decision, prompt version and model, and the counts masked in the summary; never the ticket text or the triage summary), `route.decided` (with reasons, confidence, features, versions), `tool.called`, `tool.denied`, `draft.created`, `verify.done` (entity the draft: passed, groundedness, numbers of claims and unsupported claims, violation codes, whether the LLM check ran, prompt version and model; never a claim's text, P5-04), `draft.approved` / `edited` / `rejected` (entity the draft: ticket, run and message ids, edit ratio, approved action ids, reject reason, whether a reply was sent; never the text or the note, P3-05b), `message.sent`, `ticket.claimed` / `released` / `closed`, `auth.login` / `login_failed` / `logout`, `settings.changed` (entity `setting` with the key; details `key`, `old`, `new` and the lead's `reason`, one record per changed key, P10-09), `kb.document_added` (details: `version`, `chunks`) / `kb.document_updated` (`version`, `chunks`, `chunks_written`, `chunks_removed`) / `kb.document_removed` (`chunks_removed`) — written by `make kb-load`, entity `kb_document` with the doc id, `kb.reindexed` (entity `kb_index` `kb_chunks`; details `full`, `collection`, `chunks`, `embedded`, `payload_updated`, `deleted`; written by `POST /admin/kb/reindex` and by `make kb-load FULL=1`, P5-01), `customer.erased` (entity the customer; the counts of the erasure report, P8-05), `job.ran` (actor `system` `jobs`, entity the job name, the job's report: numbers only, P8-05), `run.recovered` (`from` `checkpoint`, `restart` or `lost_resume`), `research.retry` (entity the run: number of unsupported claims searched, chunks added; never a claim, P6-04), `memory.written` (entity the ticket: memory id, length, counts masked, prompt version, model; never the text) / `memory.failed` (the error class, P6-05).

The hash chain makes changes visible: `GET /console/audit/verify` recomputes it. Masking (G1) covers the actor, action and entity fields as well as the details, numbers included. Ids given as `uuid.UUID` objects are kept unmasked, so they stay searchable; since P8-03 a string that is exactly a canonical UUID is kept by G1 too (§3; the card hidden in that shape is an accepted limitation). Any other string is masked (data model, `audit_log`). The log holds ids, codes and numbers — no names, no message text, no card data. It refers to a customer only by the internal UUID. Retention 5 years (configurable). Erasure does not touch the log: it anonymises the `customers` row, so the UUID no longer points to a person, and the hash chain stays valid.

**Known limitation: deleting the newest rows is not detected.** A hash chain proves only that the rows it has are unchanged and in order. A changed row fails its own hash, and a deleted row breaks the link of the row after it. But removing the last N rows leaves a shorter chain that still verifies (test `test_known_limitation_deleting_the_last_rows_is_not_detected`). The app role cannot delete rows (§4), so this needs the table owner or a superuser. Not fixed in this project. A fix would anchor the chain head outside the database, for example by publishing the latest `id` and `hash` periodically to a separate append-only store and comparing on verify.

## 6. Privacy (GDPR)

| Principle | Implementation |
|---|---|
| Minimisation | Models get masked text with placeholders; tools return only the fields needed; memory items are short summaries. |
| Purpose | Customer data is used to answer the ticket. Evaluation data is synthetic only. No customer data is used for training. |
| Storage limitation | Retention job (`POST /admin/jobs/retention` nightly, `make retention` by hand; `hub/privacy/retention.py`, P8-05): tickets without activity (newest message, or creation) for 24 months (`RETENTION_TICKET_DAYS`) → deleted with their messages, drafts, runs, tool calls, feedback, memory and checkpoints (`llm_calls` stay as the cost record, without their run); checkpoints of closed tickets → deleted 7 days after the close (`RETENTION_CHECKPOINT_DAYS`, the newest `ticket.closed` record); memory → deleted at `expires_at` (12 months). There are no traces (Langfuse was removed, ADR-0019). The audit log (5 years) is not deleted by the job: the app role cannot delete audit rows (§4), and removing the oldest rows would make the first remaining row fail the chain check, so it needs a decision on anchoring the chain. **Known limitation, deferred (owner decision, PR 46).** Future approach: archive the old rows, and store the hash of the last removed row as a signed chain checkpoint that verification starts from instead of the 64 zeros. |
| Erasure | `DELETE /admin/customers/{id}/data` (`hub/privacy/erasure.py`, P8-05): deletes messages, drafts, memory, feedback, checkpoints; cuts the customer's tool calls to their argument names (a Jira description or a search query can quote the customer); anonymises the customer row (name and email replaced, `anonymised_at`; `external_ref` stays so `make seed` does not bring the person back) and the ticket rows (operator summary removed; kept for statistics); a run still waiting for an operator ends `failed` (`CustomerErased`); runs and `llm_calls` hold no text and stay; the audit log is not changed (it holds only the internal id, so the chain still verifies). Returns a report of what was removed. In a real payments company the legal record-keeping duty (anti-money-laundering rules, 5 years) comes before erasure for transaction records; the Hub holds only support data, which can be erased. |
| Transparency | The chat shows the AI notice and a link to a short privacy text: what the AI sees, who the providers are, how to ask for a human. |
| Providers | Data goes to one model provider, Anthropic ([ADR-0018](adr/0018-budget-mode.md)); there is no tracing service (Langfuse was removed, [ADR-0019](adr/0019-scope-cuts.md)). Embeddings are computed locally, so knowledge-base text and queries for search never leave the host. The README lists them as sub-processors of the fictional company and names the provider settings that matter (API data is not used for training; retention options). The builder checks the current provider terms. |

## 7. EU AI Act — Article 50 (transparency)

- At the start of every conversation: "You are chatting with Tallybridge's AI assistant. It can make mistakes. You can ask for a human at any time." Stored as `tickets.ai_disclosed_at`.
- Every AI-written message has the label "AI assistant"; every operator message has the operator's first name and "Support team". An AI draft approved without changes is still labelled "AI assistant · reviewed by <name>".
- The system is a limited-risk chatbot. It makes no decisions about access to financial services (verification, restrictions and limits are decided by humans), which keeps it out of the high-risk use cases. This reasoning is written in the README as an assumption, not as legal advice.

## 8. Secure development rules for the builder

- No secret in code, tests, fixtures or docs. Test card numbers: only public test numbers.
- Never log request bodies before masking. Never put ticket text in an exception message.
- Every new model call goes through `llm/gateway.py`. Every new tool goes through `tools/permissions.py`. Direct provider or HTTP calls from nodes are forbidden (import-linter rule).
- Every new endpoint declares its role and has an authorisation test.
- A change in `guardrails/`, `tools/permissions.py`, `auth/` or `config/policy.yaml` needs the security review checklist in the pull request (template in `.github/`), and the attack suite must pass.
