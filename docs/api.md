# API Contract

Base path `/api/v1`. JSON, `snake_case`. FastAPI generates the OpenAPI file; this document is the contract the code must match. The web app generates its TypeScript types from the OpenAPI file (`make web-types`).

## 1. Conventions

- **Errors:** RFC 9457 problem details, media type `application/problem+json`: `{"type": "about:blank", "title": "Conflict", "status": 409, "detail": "...", "code": "stale_draft"}`. `type` is always `about:blank`, so `title` is the standard HTTP status phrase (`HTTP 499` for a status without one) and `code` carries the meaning. Codes:
  - codes named by an endpoint in this document, e.g. `stale_draft`;
  - `validation_error` (422): the request does not match the schema. Extension member `errors`: a list of `{"loc": [...], "type": "...", "msg": "..."}`. Submitted values are never repeated; `loc` can name a key the client sent;
  - `internal_error` (500): unexpected error. `detail` is generic; quote the `X-Request-ID` to find the log line;
  - any other HTTP error: the status phrase in snake case, e.g. `not_found`, `method_not_allowed`, `too_many_requests` (`http_<status>` for a status without a phrase).
- **Request id:** every response has an `X-Request-ID` header. A caller's own `X-Request-ID` is kept when it has 1–64 characters from `A-Z a-z 0-9 . _ -`, no run of 13 or more digits, and nothing the card-data mask (G1, which also masks the logs) would change, so the id reads the same in the logs; otherwise the API generates one: 32 lowercase letters `a`–`p` (a random UUID's hex digits mapped to letters), so it has no digits and the mask can never change it. Every log line of the request carries it as `request_id`, exactly as in the header.
- **Auth:** two cookie sessions, both `HttpOnly`, `Secure`, `SameSite=Lax`, signed.
  - `hub_customer` — demo customer session (stands for the login of the Tallybridge app).
  - `hub_operator` — operator session (8 hours from login). Every request that is not `GET`/`HEAD`/`OPTIONS` on `/console`, `/admin` and `/auth/logout` also needs the `X-CSRF-Token` header with the token from `POST /auth/login` or `GET /auth/me`. Answers: no or invalid session → `401 unauthorized`; missing or wrong token → `403 csrf_failed`; role not allowed → `403 forbidden` ([security](security.md) §4).
- **Scheduled jobs:** `POST /admin/jobs/{name}` accepts a bearer token (`JOBS_TOKEN`) instead of a session, because GitHub Actions calls it. The token works only for these endpoints.
- **Roles:** `operator` < `lead` < `admin`; `compliance` can read tickets and the audit log, and cannot change anything.
- **Idempotency:** `Idempotency-Key` header (UUID) on every POST that creates a message or runs an action; a missing or malformed key is a `validation_error`. The same key returns the first result. Keys are scoped to the caller (a customer's key never returns another customer's result). The same key sent with a different request (other text, other ticket) returns `409 idempotency_key_reused`.
- **Pagination:** `?limit=50&cursor=...`; response `{"items": [...], "next_cursor": "..."}`.
- **Rate limits (demo):** customer endpoints 10 messages per minute per session and 60 per hour per IP; login 5 tries per 15 minutes (for the demo session: 5 wrong access codes per 15 minutes per IP). Over the limit → 429 with `Retry-After`.
- **Input limits:** a request body is at most 32 KB (`413 content_too_large`, checked before the body is parsed). A customer message is at most 4,000 characters (`422 validation_error`, checked before masking, security T9). Text with a NUL character is refused with `422 validation_error` (Postgres cannot store it). Other text fields (P8-04, `tests/unit/test_input_limits.py`): operator reply, edit and reject reply 4,000 characters like a customer message; reject note and feedback comment 1,000; a hand-made Jira issue's summary 255 and description 5,000; KB search `q` 500; access code 200; login password 1,024 and email 254. NUL is refused in every stored text field.
- **Security headers** (P8-04, `hub/api/security_headers.py`): every response has `Content-Security-Policy` (`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a `Permissions-Policy` that turns off camera, microphone, geolocation, payment and USB, `Cross-Origin-Opener-Policy: same-origin` and `Strict-Transport-Security: max-age=31536000; includeSubDomains`; `/api/...` responses also `Cache-Control: no-store` (they hold personal data). A header a route sets itself wins (the SSE stream keeps its own `Cache-Control`). The FastAPI docs pages `/docs` and `/redoc` get their own policy that allows the `cdn.jsdelivr.net` bundles and inline scripts they need; with `APP_ENV=demo` they are not served (`/openapi.json` stays).
- **Time:** ISO 8601 UTC.

{
  "id": "0193…",
  "role": "assistant",
  "author_label": "AI assistant",
  "is_ai_generated": true,
  "body": "Your withdrawal of €420.00 from 9 November is still in progress… [1]",

A citation of an account fact (P7-04) has the title `Your account` and an empty `url`: it is not a help-centre page, so the chat shows it without a link. `masked` is true when the server hid card data in the message (not for a partly masked IBAN, ADR-0017) (the chat shows a note, [UI](ui.md) §2). Internal fields (chunk ids, scores, confidence, route reasons) are never in customer responses.

**Ticket object (customer view):** `id`, `status`, `ai_disclosure` (the text of [security](security.md) §7), `ai_disclosed_at`, `created_at`.

Conflict rule: every state-changing draft or ticket request sends `ticket_version`. If the ticket changed (for example the customer wrote again: every customer message changes the version, also when the status stays the same, P6-03), the server returns `409 stale_draft`. Claim, release and close answer with the ticket's queue row (with the new `version`); reply answers with the stored message; approve, edit and reject answer with `{"draft", "message", "ticket"}` (the reviewed draft, the sent message or `null`, the queue row). A draft that no longer waits (already reviewed or superseded, or the ticket is no longer `pending_approval`) → `409 conflict`; an already reviewed draft answers `conflict` even with an old `ticket_version` (checked before the version); another operator's claim → `409 conflict` (a lead may act on it); an `approved_actions` id that the draft does not propose → `422 validation_error`. Approved actions are stored with the review (`drafts.approved_actions`) and audited; `act` runs them after the resume (P7-05). Idempotency of a review: the same key with the same request (draft, outcome, final text, approved actions, reject reason and note) returns the first result; anything else, or a key a free reply already used, → `409 idempotency_key_reused`. A review made before migration 0013 has no stored key and null approved actions (no backfill, owner decision): a repeat of its key answers `409 idempotency_key_reused`, not the first result; null actions compare as "no actions". More ticked actions than the ticket may still create are refused before anything is written: more than one → `422 validation_error` (error type `too_many_actions`); the ticket already has its Jira issue → `409 action_limit_reached` (security T8: one issue per ticket).

## 4. SSE stream for a customer message

`POST /tickets` and `POST /tickets/{id}/messages` answer with `Content-Type: text/event-stream`. The browser reads it with `fetch` and a stream reader (not `EventSource`, because it is a POST).

| Event | Data | When |
|---|---|---|
| `ticket.created` | `{"ticket_id", "message": {...}}` | after the message is masked and saved |
| `run.status` | `{"step": "understanding" \| "searching" \| "writing" \| "checking"}` | when a workflow step starts; friendly labels only, no internals |
| `message` | message object | the AI answer or the handoff notice |
| `ticket.status` | `{"status": "answered" \| "pending_approval" \| "handed_off" \| "processing" \| "closed"}` | the ticket's current status when the stream ends. `processing` only when no run worked on the ticket, or the run failed and even the handoff could not be saved: the ticket waits in the operator queue. `closed` when an operator closed the ticket while the run worked |
| `error` | problem details | the run failed; the ticket goes to a human |
| `done` | `{}` | always the last event |

`POST /tickets/{id}/messages` also starts with `ticket.created`, carrying the new message.

**The run stream (P3-05; search P5-03; the graph P6-01; routing P6-02; pause P6-03).** `POST /tickets` starts a run of the workflow graph (intake → triage → policy_gate → research → write → verify → decide → human_review → act → respond; [AI pipeline](ai-pipeline.md) §1). Each `run.status` is sent when the first node of its step starts, once. The stream depends on the route ([AI pipeline](ai-pipeline.md) §6):
- **approval:** `ticket.created` → `run.status` (`understanding`, `searching`, `writing`, `checking`; B0 has no `searching` and no `checking`) → `message` (a placeholder system message, not stored) → `ticket.status` (`pending_approval`) → `done`.
- **handoff:** `message` is the stored handoff notice (`role` `system`, not AI-generated): a fixed text with the safe first step when there is one and the expected response time, sent before `ticket.status` (`handed_off`). A hard rule hands off before research, so only `understanding` is shown. When a node failed or ran past its timeout (reason `system_error`, or `budget_exceeded` after a budget stop), `error` (problem details, `code` `internal_error`, a fixed `detail`) follows the notice. The operator summary is never in the stream.
- **auto_reply** (only when a lead turned it on): `message` is the stored AI answer (`role` `assistant`), then `ticket.status` (`answered`).

When the run fails so badly that no notice could be saved, the stream sends `error` and the placeholder instead. Every run stream ends with a `message`, `ticket.status` and `done`: when no run starts (a human already has the ticket) `ticket.status` carries its current status, and when even the handoff cannot be saved it carries `processing`. The run is a task of its own: a closed stream does not stop it. `POST /tickets/{id}/messages` starts a run like a new ticket only on an `answered` ticket the AI still owns (data model §1, ownership rule; P6-03). A follow-up that starts no run (a human owns the ticket, or a run already works on it), a replayed `Idempotency-Key` and a new ticket whose masking failed: their stream is `ticket.created` → placeholder → (`ticket.status` `handed_off` after a failed mask) → `done`. A replay always carries `ticket.status` with the ticket's current status, so it never looks different from the first response (P6-01).

The server sends a comment line (`: ping`) every 10 s to keep the connection open. If the stream breaks, the client falls back to polling `GET /tickets/{id}/messages`.

Definitions (`hub/metrics/dashboard.py`, P10-09; every number is one SQL query, and `tests/integration/test_metrics_api.py` checks them on seeded rows):
- **Tickets of the period:** tickets **created** in it. A ticket's **route** and **route reasons** are those of its **first run that has a route** (how the AI routed the ticket when it arrived); later runs of the same ticket do not count again. `total` also counts tickets without a routed run (still `processing`).
- `automation_share` = `auto_reply` ÷ `total`. `ai_resolved_share` = tickets first routed `auto_reply` that are `closed` with no operator message, no run with the reason `customer_request` and no "not helpful" feedback, ÷ `total` (PRD §6). Both `null` when `total` is 0.
- `route_reasons`: each reason of each first routed run, most frequent first.
- `drafts`: reviewed drafts of the period's tickets (every run's draft); `approved_unchanged_share` = approved ÷ (approved + edited + rejected); `median_edit_ratio` over the edited drafts. `null` without data.
- `first_response_ms`: `first_response_at − created_at` of the period's tickets that have one (median and p95). `latency_ms`: `runs.latency_ms` of every run of the period's tickets. Percentiles are linear (`percentile_cont`); `null` without data.
- `cost_usd`: real-mode model calls written **in the period** with context `online` or `memory` (the rows the budget guard counts, without `record`); `per_ticket` = total ÷ the period's `total` tickets (`null` when 0); `by_node` per `llm_calls.node`. Fake-mode calls cost nothing here.
- `feedback`: ratings on the period's tickets.
- `budget`: always **today** (UTC), whatever the period: the `daily_budget_usd` setting (else `DAILY_BUDGET_USD`) and today's real-mode spend, as the budget guard computes them.

## 7. MCP server: `support-tools`

Transport: streamable HTTP at `/mcp` (Hub → server, bearer token from `MCP_SERVER_TOKEN`; a request without it gets `401`, and the server does not start without a token) and stdio (for Claude Code). Built with the `mcp` SDK 2.3.0 (`MCPServer`, `apps/mcp_server/src/support_tools/server.py`). Every tool validates its arguments against its input schema (reference formats `CUS-NNNN`, `TX-NNNNNN`, ticket id as UUID, enums, lengths) and returns structured content that matches an output schema (the Pydantic result models in `support_tools/adapters/`). Errors are returned as tool errors with a short safe message that never repeats an argument value: arguments that fail the input schema give `invalid arguments: <field names>` (`SupportToolsServer`, because the SDK's own text repeats the value); otherwise `customer not found`, `transaction not found` (the same for another customer's transaction), `issue not found`, `idempotency key reused with other arguments`, `this ticket already has a Jira issue` / `a Slack alert`; an unexpected exception reaches the client only as `Error executing tool <name>`. Dates are resolved against `CORE_ANCHOR_DATE` (empty = today in CET); every result carries `as_of`.

| Tool | Arguments | Result | Side effect |
|---|---|---|---|
| `core_get_customer` | `customer_ref` | tier, country, verification status, restriction flag (**no reason**), limits and how much is used | no |
| `core_list_transactions` | `customer_ref`, `type?`, `status?`, `limit≤20` | list: reference, type, amount, currency, status, dates, error code | no |
| `core_get_transaction` | `customer_ref`, `reference` | one transaction with status history, `expected_event` (`arrival`, `funds_available`, `review_decision`, `return_to_balance`), `expected_by` (latest CET date, business days of world file §5) and `overdue`. Only the rules the world file states: a SEPA withdrawal gets a date only when requested before 15:00 CET on a business day (none after the cut-off); Faster Payments the same calendar day; card payment requests the later of 3 business days and 7 calendar days, because the world file does not define the "new account" of its 7-day rule | no |
| `core_get_cards` | `customer_ref` | cards: last 4 digits, type, status, delivery status, `expected_delivery_by` for a physical card on its way | no |
| `jira_create_issue` | `issue_type` (`dispute` \| `fraud` \| `bug` \| `limit_request`), `summary`, `description`, `customer_ref` (must exist in the core mock), `ticket_id`, `idempotency_key` | issue key, URL, `created` (false on a replay) | yes |
| `jira_get_issue` | `key` | status, assignee | no |
| `slack_post_escalation` | `ticket_id`, `urgency`, `text`, `idempotency_key` | message timestamp, `created` (false on a replay) | yes |

Adapters: `core` reads `data/seed` (always a mock; own read-only schemas in `support_tools/seed.py`, kept in agreement with `hub.domain.seed` by a test). Limits report how much is used per currency, without conversion (the mock has no exchange rates): daily limits count transactions dated today (CET), monthly ones this calendar month. Seed events are never dated today, so the daily `used` is always empty in the demo data; the tool description says what an empty `used` means. `jira` and `slack` are mocks too: they write to a local table (a SQLite file, `MCP_MOCK_DB`) and log the key, type and ticket only. There is no real mode ([ADR-0019](adr/0019-scope-cuts.md)). Idempotency: the same `idempotency_key` with the same arguments returns the first result (`created: false`); the same key with other arguments is refused; a second issue or alert for the same ticket under a new key is refused (at most 1 issue and 1 alert per ticket, security T8). Unique indexes enforce both. Jira keys are `TB-<n>` with URLs on the reserved domain `jira.tallybridge.example`.

How the Hub exposes tools to the model during research (see [ai-pipeline](ai-pipeline.md) §4): only the four read tools plus `search_kb`, **without** the `customer_ref` argument. The Hub adds `customer_ref` from the tickets row (the `external_ref` of the ticket's customer, P7-04), never from the model. `search_kb` runs in the Hub, not on this server; it is decided and recorded in `tool_calls` like the MCP tools. Tools with side effects are never given to the model as callable tools.
